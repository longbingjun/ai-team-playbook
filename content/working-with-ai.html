8.1 工程护栏概念：Harness、AGENTS.md、CLI/MCP 与独立工作树#

这里需要明确区分两类角色：第 3 章运行在生产服务器沙箱里、为企业客户分析业务文档的是线上业务Agent；而在日常研发过程中，协助人类程序员阅读代码仓、编写功能与排查缺陷的辅助工具（如 Claude Code、Cursor 等）则是编程 Agent（Coding Agent）。编程 Agent 初次进入仓库时，仅读几个局部代码文件并不知道第 2.3 节“业务模块禁止直连底座私有表”或第 4.1 节“每次对象操作必须核验租户归属”等全局架构铁律。为了让编程 Agent 稳定产出合规代码，需要在仓库内建设一套由规范文档、验证工具与隔离环境组成的工程护栏体系，业界统称为 Harness：

第一项是仓库级规范文件：根目录的 README.md 说明本地环境搭建与启动命令；专门写给智能体与人类开发者的 AGENTS.md 则明确规定各目录职责边界、禁止跨模块读写的表范围、多租户鉴权与配额预占编码规范，以及提交前必须通过的检查命令；固定流程（如迁移脚本检查、发布前核对清单）则封装为开发期可复用的 Skill。

第二项是可验证的工具反馈通道（CLI 与 MCP）：编程 Agent 修改代码后不能只凭文本自评“已修好”，必须通过命令行界面（Command-Line Interface, CLI）实际运行第 1.1 节的 TypeScript 编译器与自动化测试套件，根据真实的进程退出码、数据库状态与接口返回报文检验结果；同时可通过模型上下文协议（Model Context Protocol, MCP，连接模型与外部数据源的标准协议）查阅内部技术文档与只读诊断日志，但生产数据库写权限与镜像发布密钥必须隔离在受控人工审批流程内。

第三项是并行开发的环境隔离工具 Git 工作树（git worktree ）。当开发者在本机同时开启两个编程 Agent会话分别开发不同功能分支时，若共用同一个目录和同一个本地测试 MySQL 库，甲会话刚写入的排队任务会被乙会话启动的 Worker 进程抢走执行。使用 git worktree 可将不同分支检出到相互独立的目录，并为每棵工作树分配独立的本地测试数据库与服务端口，实现多任务并行互不干扰。

8.2 验证与决策边界：防范同源盲区、TDD 与架构决策记录#

在借助编程 Agent 编写测试时，需要重点防范同源盲区（Correlated Blind Spots）。同源盲区是指当同一个编程 Agent 会话刚刚写完业务功能代码、紧接着又在同一上下文中编写测试代码时，它在实现阶段漏掉的并发时序或权限边界，在写测试时也会顺着相同的思维定势一并漏掉。例如测试第 7.1 节的“取消任务”功能时，实现者自写的测试往往只验证“任务尚在排队时点击取消”，而漏掉“最后一步工具执行完毕准备写回结果的那一瞬间，恰好撞上用户发起取消请求”的并发竞争。

消除同源盲区的工程做法是将实现者与独立验证者分离在两棵互不共享对话历史的独立工作树中：实现者按Spec 编写业务代码；另一名工程师或独立的验证 Agent 不看实现代码，直接依据第 7.1 节的原始 Spec 设计对抗性时序测试（例如令模拟工具在最后一步挂起，先发送取消请求再放行工具回调，随后反过来先提交完成再点取消，两轮均刷新前端页面并核对 MySQL 状态与工具调用账单）。在日常开发方式的选择上，调优前端排版与早期交互原型可采用高效的对话式快速迭代（Vibe Coding）；而第 3 章的租约代数流转、第 4章的多租户对象级鉴权与配额预占公式 U + R + B ≤ Q 等核心逻辑，则应采用测试驱动开发（Test-Driven Development, TDD），先写好覆盖正常与越界情况的自动化断言，再编写业务实现。

纵览全书八章：第 1、2 章搭建了从浏览器 HTML/React 渲染、反向代理到四通道接口与模块化单体的前后端骨架；第 3、4 章在业务模块内嵌入了抗中断的异步 Worker、Agent 循环、一次性隔离沙箱与多租户安全计量账本；第 5、6 章保障了这套系统在持续容器化升级与高负载运行下的持久可靠与性能可测；第 7、8章则确立了人与编程 Agent 共同演进这套系统的协作规约。技术组件解决的是确定性执行与边界隔离，而诸如“取消任务后已发生的外部调用成本如何分摊”“何时为大客户拆分独立存储或独立队列”等关乎商业承诺与长期维护成本的权衡，始终由人类工程师做出判断，并将背景依据与下次复查指标写入仓库的架构决策记录（Architecture Decision Record, ADR）持续传承。
