4.1 身份与权限概念：凭证保护、租户层级与对象级鉴权#

前三章搭建了从前端页面、通信接口到后台 Agent 沙箱的执行链路。当这套企业级 SaaS（Software as a Service，软件即服务）系统同时服务几十家互不隶属的客户公司时，所有客户共享同一组后端进程、同一个 MySQL 实例和同一个对象存储池。为了严防甲公司成员看到乙公司的文档或任务，后端必须在每一次请求入口处依次执行身份认证（Authentication，确认来访者是哪个账号）与权限核验（Authorization，确认该账号能否操作目标资源）。

在身份认证环节，数据库里涉及三类敏感凭证，工程上根据“未来是否需要还原明文”以及“原始字符串本身的随机程度”选用三种不同的密码学手段：第一类是用户登录密码，用户自设口令较短、容易被攻击者用密码字典高速猜解，因此后端使用故意增加计算耗时的慢哈希算法 scrypt 配合随机盐值生成摘要存入MySQL，不可逆且防暴力破解；第二类是登录成功后发放的不透明会话令牌（Opaque Session Token），它本身是由后端生成的长随机字符串，数据库只需保存其快速的 SHA-256 哈希值用于每次比对和主动注销，前端浏览器则通过同时开启了 HttpOnly （禁止第 1.1 节前端 JS 脚本读取，防脚本窃取）、Secure （仅经第 1.2 节 HTTPS 加密通道发送）和 SameSite （阻断跨站伪造请求）三项安全属性的 Cookie 自动携带该令牌；第三类是客户托管在系统里供第 3.3 节模型适配层代为调用的外部 API 密钥，由于后台调用时必须还原出明文密钥，后端采用可逆的对称加密算法 AES-256-GCM 加密落库。

完成身份认证拿到当前用户编号（user_id ）后，权限核验依托“用户 — 租户 — 项目”三层归属模型展开。租户（Tenant，标识为 tenant_id ）是指系统中独立签约、独立拥有数据与配额权益的客户企业或组织；一名用户可能受邀加入多个企业租户，单个租户下又可按业务部门划分多个项目（project_id ），这也正好对应了第 1.3 节前端 TanStack Query 按“账号 + 企业空间 + 资源编号”隔离本地缓存的设计。在后端，所有任务、文件和事件在写入 MySQL 时均绑定所属的 tenant_id 与 project_id 。此后无论是第 2.1节查询列表、第 2.2 节订阅 SSE 进度、第 3.1 节取消任务，还是凭产物编号 a_5 请求下载文件，后端每次都必须核实当前登录会话在该租户与项目下对 a_5 拥有访问权，这项机制称为对象级鉴权（Object-Level Authorization，详见 OWASP API1:2023 对象级授权规范）。仅靠难猜的随机文件名不能代替服务端鉴权；若业务要求将某员工移出项目后立即阻断其下载权限，下载通道就应采用逐次经过后端对象级鉴权的流式转发，而非有效期内可反复直连的预签名下载链接。

4.2 存储计量机制：共享对象存储池与配额预占模型#

在多租户文件存储层面，如果每开通一家新企业租户就在云平台上新建一个独立存储桶，租户增多后会触及云账号的桶数量上限，备份与权限配置也会高度碎片化。常规做法是让所有普通租户共用第 1.2 节的同一个私有对象存储池，在对象路径最前面加上 tenant_id 前缀区分目录，并由 4.1 节的服务端对象级鉴权严格把关读写范围（详见 AWS 多租户对象存储设计；仅当大型客户有特定地域合规或自持密钥要求时再单独挂载专属桶）。在此结构下，容量核算需要区分两本账：销售套餐承诺给单个租户的 100 GB 上限（按十进制 1 GB = 109 字节计）是记录在 MySQL 平台底座里的逻辑配额账本；存储池底层真实的磁盘空间则是运维物理容量。100 家租户全部存满时，正式文件合计 10 TB，运维物理容量还需额外覆盖底层多副本冗余、历史保留版本与第 3.3 节沙箱运行期间的临时文件峰值。

逻辑配额账本与第 2.2 节大文件预签名直传、第 3.3 节沙箱产物转正配合时，如果等到文件彻底写完才检查并累加已用空间，并发写入就会突破套餐上限。设某租户配额上限为 100 GB，当前已确认占用 92 GB；此时该企业的两名成员同时发起各 6 GB 的文件上传。若后端在签发预签名链接前只简单读取“当前已用 92 GB，再加 6 GB 不超过 100 GB”，两笔请求都会获批上传，传完后实际占用将达到 104 GB。要堵住这一并发漏洞，必须在写入开始前先把在途申请量锁进账本。设租户配额上限为 Q，已确认正式文件占用量为 U，当前正在上传的文件与沙箱待转正产物的预留字节总和为 R，本次新申请写入的字节上限为 B。后端在签发第 2.2 节预签名上传链接或执行第 3.3 节产物转正前，先在 MySQL 事务中锁定该租户的配额行，校验如下不等式：

U + R + B ≤ Q

将上述算例代入公式（Q = 100 GB，U = 92 GB，初始 R = 0）：第一笔 6 GB 请求计算得到 92 + 0 + 6 = 98 ≤100，校验通过，事务立即写入一条 6 GB 预留记录，账本变为 U = 92 GB、R = 6 GB（若该次点击因网络波动触发第 3.1 节幂等重试，后端凭幂等键找回原预留，不重复扣减）；随后到达的第二笔 6 GB 请求计算得到92 + 6 + 6 = 104 > 100，当场被拒绝。待第一笔文件上传完毕，后端向对象存储核实真实字节数：若申请上限预留了 6 GB、实际上传文件为 5 GB，结算事务便从 R 中扣去 6 GB、向 U 中增加 5 GB，账本更新为 U =97 GB、R = 0 GB。后台定时对账任务还会扫描超时未完成上传的僵尸预留予以回收，并在正式文件删除且解除全部引用后幂等退还一次配额。

4.3 服务端出境边界：响应脱敏与自研 Skill 保护#

回顾第 1.2 节提到的浏览器 F12 开发者工具原理：凡是离开后端发往客户端的数据，包括第 1.1 节打包的前端脚本、第 2.1 节的 JSON 响应、第 2.2 节的 SSE 事件流、报错提示以及可下载文件，对当前登录用户而言全部属于公开可见内容。如果后端把外部大模型供应商返回的原始调试报文原样塞进 JSON 字段、只靠前端界面隐藏不显示，或者在 REST 接口做了过滤、却在 SSE 报错事件里直接输出了服务端异常堆栈，供应商内部地址与服务器目录结构就会直接泄露。因此，所有上游原始响应都必须在后端清洗并转换为自有公开格式后再发往前端。

团队在业务模块中沉淀的专有 Skill（领域技能包）同样受这条出境边界约束。Skill 是将特定业务领域的提示词模板、参考脚本与输出校验规则封装在一起的可复用能力包。如果某项 Skill 中包含企业高价值的专有评估标准或定价规则，仅在提示词里嘱咐大模型“请勿向用户透露本段规则”很容易被套话绕过（详见OWASP 系统提示词泄露风险文档），需要沿着构建分发、模型运行与沙箱交付三条路径分别建立服务端隔离。

传播路径泄露成因服务端隔离方案
1. 代码打包与镜像分发第 1.1 节前端打包产物、公开代码仓或外发容器镜像层中混入了私有提示词与密钥前端与公开包按白名单导出；专有 Skill 仅放入受控后端仓库与私有镜像，密钥在启动时动态注入
2. 运行时模型调用将保密规则全文放进提示词或第 3.3节沙箱只读目录交给模型阅读，被模型在对话中复述拆分“给模型看的公开参数说明”与“保密算法代码”：核心规则写成后端内部函数，仅向模型返回计算后的结构化结果
3. 沙箱产物打包下载沙箱将临时工作目录直接压缩供用户下载时，把内部模板或未授权中间文件一并打入包内沙箱产物先在不可见暂存区核对文件类型、解压体积与白名单；固定版式报告由后端可信程序按结构化数据生成
