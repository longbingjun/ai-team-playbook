3.1 队列调度概念：工作进程、三层记录、幂等键与租约栅栏#

第 2.2 节提到，用户在业务模块页面点击运行分析后，Express API 进程往 MySQL 写入一条排队记录便立刻返回 202 Accepted 。接下来谁在后台把这条记录真正做完，并且保证遇到断网重发、多台机器争抢或服务器意外重启时既不重扣费用也不丢任务？这需要先明确后台队列调度的四组核心概念：

第一组是进程（Process）与工作进程（Worker）。进程是操作系统中正在独立运行的一份程序实例。为了不让长达几分钟的模型推理占满网页接口资源，后端把同一套代码分别启动为两类进程：API 进程专门快速响应网页请求，Worker 进程不对外接收网页访问，专门在后台循环扫描待办任务队列并执行耗时计算。

第二组是三层任务记录模型。假设用户提交了任务 r_17 ，1 号 Worker 执行到一半时所在机器断电重启，2号 Worker 随后接手重跑并生成了报告。从前端用户视角看，自己只发起过一项任务，列表里只能有一条记录；但从后端运维与财务核账视角看，后台实际跑过两次，且第一次中断前可能已经发生过外部付费调用。为此数据库把数据拆成三层编号：任务（Run）代表用户发起的这一项工作及最终结果；执行尝试（Attempt）记录某一台 Worker 从领取到结束的单次运行过程；工具动作（Action）记录单步外部接口或工具的调用明细。应用初期可直接用 MySQL 的任务表充当队列；若日后引入独立的内存数据库 Redis 分发待办通知，为了防止“MySQL 已提交成功、进程却在向 Redis 发通知前崩溃”导致丢单，可采用事务发件箱（Transactional Outbox）模式：在同一个 MySQL 事务里同时写入任务行和一张本地“待发消息表”，再由独立转发程序把消息投递给 Redis。

第三组是入口防重的幂等键（Idempotency-Key）。幂等性是指同一个操作无论因网络超时被重复提交多少次，系统产生的业务结果都与只执行一次完全相同。用户点击开始按钮时，React 前端生成一个随机字符串作为幂等键随请求发给后端，未收到明确结果前的自动重试都携带同一个键。注意后端不能只靠“先SELECT 查询该键是否存在，不存在再 INSERT ”来防重，因为两笔并发重发请求可能在同一毫秒都读到“不存在”并双双插入。后端必须在 MySQL 中为“租户 + 用户 + 操作类型 + 幂等键”建立唯一约束，并保存输入参数的哈希摘要：两笔相同请求同时到达时，数据库保证只有一笔插入成功；另一笔捕获唯一约束冲突后核对摘要一致，直接返回原任务编号 r_17 （若摘要不一致则返回 409 Conflict 报错）。

第四组是出口防撞单与防覆盖的锁定跳过（SKIP LOCKED）、租约（Lease）与栅栏令牌（Fencing Token）。多台 Worker 同时扫描 MySQL 待办表时，执行带 SELECT ... FOR UPDATE SKIP LOCKED 的短事务领单（详见 MySQL 8.4 锁定读文档）：遇到正被其他 Worker 锁定的行不阻塞等待，直接跳过并锁定下一条空闲任务，将其标为运行中（running ），写入有期限的租约到期时间（lease_until），同时把每次领单自动加 1 的执行代数（lease_generation）递增，随即提交事务释放数据库锁。Worker 正常运行时定时续期租约；机器宕机后租约过期，新 Worker 接手并使代数从 1 升为 2。倘若第 1 代 Worker 只是网络卡顿一分钟后恢复，拿着算出的旧结果回来写库，递增的执行代数就充当拦截旧写入的栅栏令牌：写回结果的更新语句强制校验 WHERE id = :run_id AND lease_generation = :generation AND lease_until >CURRENT_TIMESTAMP ，第 1 代携带过期代数值更新时受影响行数为 0，据此放弃发布旧产物。图 3.1 汇总了单条任务在后台经历的完整状态流转。

3.2 智能体核心概念：Workflow、Agent 与 RAG#

Worker 从队列里领到任务后，内部具体怎样借助大语言模型（LLM）完成业务分析？按执行步骤是否预先写死，工程上区分为两类核心模式，并常搭配私域检索组件（参见 Anthropic 对工作流与 Agent 的区分）：

确定性工作流（Workflow）是由开发者在代码中预先规定好固定步骤与分支走向的自动化流程。例如“读取指定文档 → 调用模型按固定 JSON 格式抽取五个字段 → 用代码校验日期与金额格式 → 写入业务表”。在Workflow 中，大模型只负责完成其中某一步文本转换，先做哪一步、后做哪一步完全由后端代码控制，成本、耗时与重试位置都高度可预测。

自主智能体（Agent）是由大语言模型根据目标与环境反馈自主决定下一步调什么工具、走多少轮循环的运行机制。面对“结合项目资料核查这份供应商方案的潜在风险”这类开放任务，事先无法写死需要查几份文件。程序把任务目标、当前上下文与可用工具清单（工具名称、用途说明与参数格式）交给模型，按“思考（Thought）→ 行动（Action）→ 观察（Observation）”循环推进：模型先在 Thought 中分析现状，在Action 中输出拟调用的工具名和参数；后端程序执行该工具，把返回结果整理为 Observation 拼入下一轮历史，供模型继续推理（常见组织范式包括边想边执行的 ReAct，以及先生成分步计划再依次求解的 Plan-and-Solve）。

检索增强生成（Retrieval-Augmented Generation, RAG）是在调用大模型生成回答前，先从外部受控文档库中检索相关片段注入上下文的技术机制。大模型的预训练参数里没有客户上传到第 1.2 节对象存储中的私有合同，而把几百页文档整本放进提示词又昂贵且缓慢。使用 RAG 时，系统预先将上传文档切分为段落切片并建立关键词与向量索引；Agent 在循环中发起检索请求时，检索工具只在当前任务获批访问的文档范围内找出最相关的几个切片，连同来源文件编号与位置返回给模型；最终生成报告后，后端还会反向核查文中引用是否确实出自本轮检索结果，防范模型编造出处。在实际企业业务模块（图 2.1 下半部）中，通常用固定 Workflow 管住主干阶段，仅在需要动态查阅资料的子步骤中启动挂载了 RAG 工具的 Agent。

3.3 运行时架构串联：Worker、Agent Runner 与隔离沙箱#

在 3.2 节的 Agent 循环里，大模型输出的 Action 本质上只是一段待核实的文本建议。如果模型受输入文档中的恶意文字诱导（提示词注入），输出了“读取其他客户文件”或“运行删除脚本”的工具参数，后端不加拦阻直接执行就会酿成安全事故。为此，系统将后台执行进一步拆分为 Worker、Agent Runner（智能体运行器）与一次性隔离沙箱（Sandbox）三层，并与第 2 章的文件和 SSE 通道闭环衔接，如图 3.2 所示。

对照图 3.2 走通一次完整执行：Worker 领到任务后启动 Agent Runner。Runner 是管理单次 Agent 循环的协调组件：它首先锁定本次任务对应的模型版本、提示词版本与输入文件版本快照，并通过模型适配层（Adapter）屏蔽不同大模型供应商的接口差异（外部 API 密钥仅保存在后端受信任配置中，同时将阶段事件写入数据库供第 2.2 节的 SSE 通道推送给前端）。每当模型请求调用工具（例如用户本次只授权了对象存储里的文件 f_8 ，模型却提出读取文件 f_9 ），Runner 都会按本次任务的授权清单拦截对 f_9 的越界请求；同时限制最大循环轮数、总耗时与 Token 预算，遇到删除记录或对外发送邮件等不可逆动作时，先暂停任务等待前端用户点击确认。

当工具需要运行模型生成的统计代码或解析复杂附件时，Runner 会启动右侧的隔离沙箱（Sandbox）。沙箱是操作系统资源与访问权限受到严格裁剪的临时运行容器：它以非 root 普通用户运行在只读系统目录上，只读挂载获准读取的输入文件 f_8 ，仅开放一块有字节上限的临时目录供写入，默认断开公网连接（确需访问外部接口仅走白名单代理），限制 CPU、内存和最大子进程数，且严禁将宿主机的容器管理套接字（如 docker.sock ）挂载进沙箱，防止沙箱内代码借此接管整台宿主机。循环结束时，Runner 对沙箱暂存区做四步检查：模型是否给出了回答、回答结构是否合规、引用的输入是否属于本任务、声明生成的产物文件是否真实可读。若模型声称“报告已生成”但暂存区并无该文件，Runner 会判定本次尝试未完成；全部核验通过后，才将产物正式存入第 1.2 节的私有对象存储并由 Worker 核对栅栏代数写回 succeeded 。
