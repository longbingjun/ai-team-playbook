7.1 研发协同概念：PRD、技术规约（Spec）与纵向切片#

在理解了全套技术架构后，接下来看开发团队如何在这套架构上协作新增一项真实功能。由于全栈功能往往同时横跨第 1 章的 React 界面、第 2 章的 API/SSE 接口以及第 3 章的 MySQL 状态机与 Worker 进程，如果拿到一句模糊需求就各自埋头写代码，前后端对异常边界的处理极易脱节。规范的工程研发通常依托三项核心文档与交付概念推进：

第一项是产品需求文档（Product Requirements Document, PRD），它是从用户与业务视角说明“为什么做、提供什么功能、遵循哪些业务规则”的书面约定。第二项是技术规约（Specification，简称Spec），它是将 PRD 转化为前后端接口格式、数据库状态转换条件与异常竞争处理规则的精确工程说明书。先对齐 PRD 与 Spec 再动手编写代码与测试的开发方式，称为规约驱动开发（Spec-Driven Development, SDD）。第三项是纵向切片（Vertical Slice），指不按“第一周只画全部前端页面、第二周只写全部后端接口”做水平分层，而是每次挑选一个最小可用子场景，一次性把穿过 React、Express、MySQL 到 Worker 的端到端链路完整打通并验收。

以给系统增加“取消任务”功能为例：用户在前端看到任务处于“运行中”，发现选错了上传文件，想点取消重做。若没有 Spec 约束，前端直接显示“已取消”、后端粗暴改写状态字段，后台正在跑的旧 Worker稍后仍可能把错文件算出的结果覆盖写回。采用规约驱动开发时，PRD 先明确业务规则：排队中任务可直接取消；运行中任务允许请求停止，并向用户提示“已发出的外部模型调用可能产生无法退回的消耗”。随后 Spec 精确规定关联第 3.1 节图 3.1 的状态机规则：排队态（queued ）取消后直接改为 cancelled ，Worker 领单时跳过；运行态（running ）收到停止请求后，API 先写入 cancel_requested ，React 页面据此显示“正在取消”，Worker 在两步工具调用之间的检查点停下后续步骤并改为 cancelled ；若最终结果在取消请求落库前已抢先提交，则由数据库条件更新保留 succeeded 。编码时分两个纵向切片推进：第一刀先只打通“暂停本地 Worker → 创建排队任务 → 页面点取消 → 刷新确认保持已取消 → 启动 Worker 验证自动跳过”；跑通四层基础配合后，第二刀再集中实现运行期停止信号传递与收尾竞态。

7.2 代码仓组织概念：Monorepo、主子分仓与三方合并#

对应第 2.3 节图 2.1 中“公共平台底座 + 多个独立业务模块”的架构，团队管理源代码仓库也有两种常见模式：

在团队规模不大时，最直接的方式是单代码仓（Monorepo），即把公开站点、核心业务前端、后端底座、各业务模块与 Worker 放在同一个 Git 仓库的不同子目录下管理。一次 Git 提交就能同步改好 React 按钮、tRPC 接口类型与后端状态转换，编译期即可发现跨层不匹配。

当某个垂直业务模块（如图 2.1 中的业务模块 A）由专门的算法与业务小组独立迭代时，也可拆分为主仓库（Host Repo）+ 业务模块子仓库（Module Sub-repo）：主仓库维护登录鉴权、配额账本、数据库迁移与第 5 章的容器打包发布；子仓库只维护该模块的前端页面、专有 Skill 与工具逻辑。为确保分仓开发合入主仓时不出错，需执行四条协作规则：一是为子仓库提供内置固定测试账号与可暂停模拟工具的独立预览壳（Standalone Preview Shell），让模块开发者无需在本地启动全套主系统就能调试“正在取消”等交互状态；二是用自动脚本强制检查模块的路由前缀与 MySQL 表名前缀，防止不同模块重名冲突；三是子仓库只声明第三方库兼容范围，最终打包运行的具体版本号统一由主仓库的依赖锁文件（Lockfile）决定；四是两边基于同一提交基线并行修改后，集成时采用三方合并（Three-Way Merge），即以双方共同出发的基线版本为参照合并两侧各自新增的修改，避免晚提交的代码覆盖掉另一侧的改动，合并后在主仓环境中用两个不同租户的测试账号核验第 4.1 节的跨租户取消拦截。
