5.1 交付基础概念：Git、CI/CD、容器镜像与不可变摘要#

前四章完成的公开站点、核心业务前后端、异步 Worker、隔离沙箱与 MySQL 数据库上线运行后，开发团队每周仍要持续修复缺陷并发布新功能。如果在生产服务器上直接拉取源码手工运行 Vite 打包和代码编译，不仅会抢占线上业务 CPU 与内存，还会因为开发机与服务器操作系统依赖库的小版本差异导致部署失败。现代工程通过代码版本控制、持续集成与容器化技术把软件交付变成标准化流水线，涉及五项基础概念：

第一项是 Git 与提交哈希（Commit SHA）。Git 是管理源码变更历史的版本控制系统，每次代码合并进主干分支都会生成一串唯一的 Commit SHA 标识，精确对应这一时刻的全套源码。第二项是持续集成与持续交付（CI/CD，常用 GitHub Actions）：每当 Git 主干收到新合并请求时，云端构建机在干净环境中按锁文件安装依赖，自动执行第 1.1 节的 TypeScript 类型检查与自动化测试，测试通过后自动打包发布物。

第三项与第四项是容器镜像（Container Image）与容器（Container）。Dockerfile 是一份记录环境安装与编译步骤的文本配方；构建工具按 Dockerfile 执行第 1.1 节的 Vite 前端构建和第 1.2 节的后端编译，把程序代码、Node.js 运行环境与系统依赖库一起打包成一份静态只读文件包，即容器镜像，并推送到镜像仓库（如 GitHub Container Registry, GHCR）。镜像本身由一层层只读快照叠加而成，因此绝不能在Dockerfile 前几步拷入私钥、再在末尾用 RUN rm 删除，否则较早的只读层里仍会永久残留密钥字节。服务器拉取镜像后启动起来的隔离运行进程就是容器：第 3.1 节的 API 进程与 Worker 进程完全共用同一份后端应用镜像，仅靠启动命令区分角色；第 3.3 节的隔离沙箱则使用剔除了多余网络工具的精简专用镜像。

第五项是镜像摘要（Image Digest，详见 Docker 镜像摘要文档）。镜像标签（Tag，如 latest 或 v1.2 ）只是方便人工阅读的别名，随时可能被新推送的同名镜像覆盖；而形如 sha256:... 的镜像摘要是由镜像内容计算出的唯一密码学指纹。生产部署清单直接锁定 sha256 摘要，才能保证线上运行的容器与 CI 测试通过的镜像字节级完全一致，故障回滚时也能精准切回上一版摘要。

5.2 持久化与容灾概念：挂载卷、兼容迁移与 RPO/RTO#

容器的设计原则是“随时可销毁替换”：每次升级新版本镜像时，旧容器会被停止并删除，容器自带的内部可写目录也会一并清空。对于无状态的 API 和 Worker 进程，直接换新容器即可；但第 1.2 节的 MySQL 数据库若直接把表文件写在容器内部，升级一次程序就会丢光全部业务数据。为此需要引入三组持久化与容灾概念：

第一组是数据挂载（Mount），包括 Docker 管理的命名卷（Volume）与指定宿主机目录的绑定挂载（Bind Mount）（详见 Docker 卷文档 与 绑定挂载文档）。挂载是将容器内部的数据路径（如 MySQL 默认存放数据的 /var/lib/mysql ）映射到宿主机外部独立数据盘路径（如 /data/mysql ）的机制。替换上方容器时，下方宿主机数据盘里的文件原封不动地保留下来供新容器继续读写。需要注意服务器重启顺序：系统启动脚本必须先确认独立数据盘已成功挂载到 /data/mysql ，再启动 MySQL 容器；否则该路径会退化为系统盘上的空文件夹，导致 MySQL 误以为首次安装而初始化出空白库。

第二组是数据库迁移（DB Migration）与健康探针。当新版代码需要给 MySQL 表新增字段（如增加第 3.1节的取消请求状态）时，开发者将 SQL 变更写成带递增编号的迁移脚本随 Git 仓库管理。为了不打断升级瞬间仍在运行的旧 Worker 任务，表结构修改遵循“先兼容扩展、后清理收缩”原则：先新增新旧两版代码都能读写的兼容字段，等旧 Worker 把手头租约内的任务处理完退出后，后续版本再移除旧字段。新容器启动后，部署脚本依次访问存活接口 /healthz （确认进程未崩溃）和就绪接口 /readyz （确认 MySQL 连接、最新迁移表与磁盘挂载全部正常），再放行外部流量。

第三组是衡量灾备有效性的两项核心指标：RPO（Recovery Point Objective，恢复点目标）指发生硬件损毁时业务最多可容忍丢失最近多长时间内产生的数据（决定了备份频率）；RTO（Recovery Time Objective，恢复时间目标）指从故障发生到全套系统恢复正常访问最多允许耗费多长时间（决定了恢复流程熟练度）。备份不能只存在本机同一块硬盘上，必须将 MySQL 备份与私有对象存储跨可用区或跨机房保存，并定期在空白隔离主机上演练完整恢复。

5.3 部署架构串联：上线流水线与发布期磁盘容量核算#

图 5.1 将 5.1 节的持续集成镜像流转与 5.2 节的宿主机持久化挂载串联成了完整的生产交付架构（单机或中小规模环境常通过编排工具 Docker Compose 统一管理反向代理、公开站点、业务 API、Worker 与数据库容器）。

在图 5.1 第 4 步的生产主机上，需要特别防范“发布期临时磁盘峰值叠加”引发的宕机。平时运行看似充足的磁盘空间，在发版窗口会同时承受三笔临时开销：设主机当前剩余可用空间为 12 GiB（按二进制 1 GiB = 2³⁰ 字节计），拉取并解压新版容器镜像层需要 5 GiB，执行数据库迁移前在本地导出一份临时快照备份占去6 GiB，恰逢第 3.3 节正在运行的沙箱临时工作区写入 3 GiB 中间文件；三笔峰值重叠共需 14 GiB，超出 12 GiB 剩余空间，导致迁移中断报错。因此生产环境需按挂载点设定配额与自动回收策略：用户长期文件一律存入私有对象存储，MySQL 二进制日志（Binlog）按恢复窗口设置自动过期，沙箱临时目录随任务结束立即清理，本机仅保留当前版与上一版可回退镜像，数据库备份直接流式上传至异地存储。
