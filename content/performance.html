6.1 性能观测概念：首屏指标、数据库索引与全链路 Trace#

当线上用户反馈“系统反应慢”时，问题可能出在第 1 章的前端静态资源加载、第 2 章的后端同步查询接口，或是第 3 章的后台异步任务队列。动手修改架构前，需要先掌握对应这三段链路的观测指标与诊断概念：

第一段是衡量第 1.1 节前端网页打开速度的两项核心指标与加速组件：TTFB（Time to First Byte，首字节时间）指浏览器发出请求到收到服务器首个响应字节的耗时；LCP（Largest Contentful Paint，最大内容绘制，详见 web.dev LCP 加载时间分解）指首屏主要内容在屏幕上渲染完成的耗时。若外地用户下载静态脚本缓慢，可引入 CDN（Content Delivery Network，内容分发网络）：CDN 是分布在各地边缘机房的缓存节点网络，能将公开展示页面与带内容哈希的 .js 、.css 静态文件缓存在离用户最近的节点就近下发（但凡带第 4.1 节登录身份的业务接口响应，必须设为私有缓存，严禁被公共 CDN 缓存导致跨租户串号）。

第二段是影响第 2.1 节同步列表读取速度的联合索引（Composite Index）与 N + 1 查询。数据库索引相当于按指定列排好序的查找目录：当业务列表经常按“租户编号 + 创建时间倒序”筛选任务时，建立(tenant_id, created_at) 联合索引即可直接定位目标记录，避免逐行扫描整张大表。N + 1 查询则是常见的 ORM 编码性能缺陷：代码先执行 1 条 SQL 查出当前页的 20 条任务，随后在循环里又单独执行 20 条SQL 去查每条任务的发起人姓名，一共发起 21 次数据库通信；将其改为 1 次批量 WHERE id IN (...) 查询或表关联，并把已完成任务的统计摘要直接落库保存，即可大幅缩短接口耗时。

第三段是定位第 3 章异步长任务瓶颈的全链路追踪（Trace）。Trace 是用一个统一的追踪标识把“前端请求→ 任务入队 → Worker 领单 → 模型与工具调用 → 产物落库”串联起来并记录各阶段时间戳的观测机制。图 6.1 将这三段延迟切面的观测位置与治理手段汇总在一起。

以图 6.1 右侧的异步任务为例演示一次定量推算：假设 Trace 记录显示某任务端到端耗时 21 秒，其中在队列里排队等了 14 秒、模型推理与工具执行占 6 秒、产物写库占 1 秒。此时去优化写库 SQL 最多只能省下不到 1 秒，真正的延迟大头是 14 秒排队。接着核算吞吐容量：每项任务占用 1 个 Worker 执行槽 6 秒，若服务器 CPU、对象存储与外部模型接口均未见顶，单个执行槽每分钟最多处理 60 ÷ 6 = 10 项任务；当线上每分钟持续涌入 15 项任务时，将 Worker 并发槽扩充至 2 个以上并留出缓冲余量即可消除积压。但若排队是因为外部大模型账号本身的每分钟并发限额已满，盲目增加本地 Worker 只会让更多请求同时撞上限流报错；此时应在任务受理入口提示预计等待时间，并限制单个租户同时运行的任务数（更换模型或提示词模板时，同样依托固定评测集对比完成率、质量与单次费用）。

6.2 架构演进对照：Dify、n8n 与 GitLab 的拆分边界#

把本书前五章搭建的“前后端双站点 + 模块化单体后端 + 独立 Worker + 一次性隔离沙箱 + 关系数据库与私有对象存储”架构，与业界三套广泛使用的开源系统做横向对比，可以验证各组件拆分的合理时机。

开源系统服务角色与存储划分与本书架构的对应关系及演进启示
Dify划分为前端 Web、后端 API、异步Worker、插件服务与独立代码沙箱；API 与 Worker 共用同一镜像按不同命令启动印证了第 3.3 节与第 5.1 节的分工：同镜像区分 API 与 Worker，在需要运行不可信动态代码时单独拆分受限沙箱容器
n8n（队列模式）主节点接收触发请求后将执行编号推入Redis，多台 Worker 节点从数据库读取上下文并行执行后写回结果印证了第 1.2 节与第 3.1 节的结论：多台机器水平扩展 Worker 时，任务依赖的上传文件必须放在共享的私有对象存储中，不能存在单机本地目录
GitLab采用模块化主应用架构：Puma 处理同步网页与 API，Sidekiq 处理后台异步队列，PostgreSQL 存关系表，大附件存对象存储印证了第 2.3 节的选择：把慢计算移入后台Worker、把大文件移入对象存储后，单套模块化单体足以长期稳定支撑复杂企业业务

由此可以提炼出清晰的技术投入优先级：第 4 章的多租户对象级鉴权、并发配额预占与专有资产出境隔离属于安全与账本正确性底线，上线首日即须完备；而引入独立 Redis 队列、多机扩展 Worker 或接入CDN，则属于容量优化手段，应当在图 6.1 的监控指标实测触及阈值后再按需演进。
