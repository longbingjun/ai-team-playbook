2.1 结构化通信概念：API、REST 与 tRPC#

在第一章的核心业务系统中，React 前端运行在用户浏览器里，Express 后端与 MySQL 数据库运行在服务器上。两端隔着互联网，前端每一次读取列表或提交表单，都需要按事先约定的格式向后端发请求。API（Application Programming Interface，应用程序编程接口）就是服务端向调用方公开的请求地址、输入参数格式与返回数据结构的统称。在 Web 系统中，结构化数据读写最常采用两种 API 组织方式：

第一种是 REST（Representational State Transfer，表述性状态转移），它是一套基于标准 HTTP 协议的接口设计风格：用 URL 路径表示要操作的业务资源（例如 /api/runs 表示任务集合，/api/runs/r_17 表示编号为 r_17 的单条任务），用 HTTP 请求方法表示动作类型（如 POST 创建记录、GET 查询记录），请求与响应正文通常采用通用的 JSON 文本格式。由于任何编程语言都能收发标准 HTTP 与 JSON，REST 非常适合编写供外部第三方系统回调、命令行工具调用，以及承接第 1.3 节公开站点跨服务请求的模块 HTTP API。

第二种是 tRPC（TypeScript Remote Procedure Call，面向 TypeScript 的远程过程调用框架）。在核心业务系统内部，有大量只供自家 React 前端调用的读写操作（如修改项目成员角色、保存界面配置）。如果全部手写 REST 接口，前端和后端必须分别维护数据类型声明；后端一旦修改了某个返回字段的名称，前端代码在编译阶段难以自动察觉。使用 tRPC 时，开发者在 Express 后端定义好处理函数的输入校验规则与返回值后，tRPC 直接将该函数的第 1.1 节 TypeScript 类型导出给前端工程引用。前端发起网络请求时就像调用本地函数一样带有自动补全，字段名不一致会在 Vite 编译阶段直接报错。需要注意，tRPC 简化的只是开发期的类型同步，程序上线后浏览器发出的依然是经过公网的 HTTP 请求，后端仍须逐次校验登录状态与操作权限。

2.2 大文件与长耗时通信：预签名链接、异步受理与 SSE#

2.1 节的 REST 与 tRPC 适合传输几百字节到几十千字节的 JSON 配置数据；但在包含 Agent 能力的业务模块中，还会遇到“上传几十兆业务文档”和“等待数分钟模型推理结果”两类特殊通信场景，需要专门的传输机制配合。

针对大体积文件读写，如果把一份 80 MB 的文档编码成 Base64 字符串放进普通 JSON 接口传输（每 3 个二进制字节会变成 4 个文本字符），数据体积会膨胀约三分之一，且后端 Node.js 进程必须将整份文件读入内存，几名用户同时上传就会耗尽后端内存。工程上为此引入预签名链接（Presigned URL）：预签名链接是由后端使用第 1.2 节私有对象存储的密钥临时签发的一串带数字签名的特殊网址，内部写死了允许写入的目标路径、动作类型（如仅限上传）、最大字节数与几分钟的有效期。用户上传大文件时，前端先请求后端核对权限与配额并在 MySQL 中登记一条“待上传”记录；随后前端拿到后端签发的预签名链接，直接将文件字节流上传至对象存储，绕开后端服务器内存；上传完毕后，后端再向对象存储核实实际文件大小与哈希摘要，确认无误后将数据库记录改为可用状态（几兆以内的小附件则可直接走后端受控文件接口流式转发）。

针对耗时数分钟的 Agent 分析任务，如果前端发出创建任务的 HTTP 请求后一直保持同步等待，一旦超过第 1.2 节反向代理的超时上限（通常为 60 秒）或遇到网络闪断，连接就会中断，用户既拿不到结果，也无法得知后台是否已经开始扣费执行。为此需要采用异步受理机制：后端把新任务写入 MySQL 数据库排队后，不等待模型计算，立刻向前端返回 HTTP 202 Accepted （已受理）状态码与任务标识（如 r_17 ），将“接收请求”与“后台执行”拆开。

前端拿到任务标识 r_17 后，获取后续进展有两种通信方式。轮询（Polling）是由前端每隔固定秒数（如3 秒）主动调用一次查询接口读取最新状态，实现简单，适合只需展示“排队中”“运行中”“已完成”阶段变化的场景。若界面需要实时逐字展示 Agent 的推理过程与生成正文，频繁轮询会产生大量无新内容的空请求，此时采用 SSE（Server-Sent Events，服务端发送事件，详见 MDN SSE 与事件编号文档）。SSE 是基于单条长 HTTP 连接由服务端向浏览器单向持续推送文本消息的通信协议：后端每产出一段新文字或工具状态，就附带递增的事件编号推送给前端；网络闪断重连时，浏览器自动带上最后收到的事件编号请求补发遗漏消息，若服务端短期缓冲已过期则先返回一份完整任务快照再继续推送。流式消息仅用于界面实时展示，任务的最终状态与正式产物始终以 MySQL 数据库记录为准。

2.3 后端架构串联：四通道接口与模块化单体#

把 2.1 节与 2.2 节的四类通信通道汇集到后端入口后，还需要规划后端内部的代码组织结构。如果在起步期就把账号认证、文件管理与各个 AI 业务模块拆成十几个独立部署的微服务（Microservices），原本在同一个进程内依靠第 1.2 节单个 MySQL 事务就能原子完成的“校验项目成员 + 预扣存储额度 + 写入待办任务”，就会变成跨网络的多次远程调用，任何一步超时都会引发数据不一致；反之，如果所有代码混在同一目录、任由各业务线随意跨表读写数据库，修改一张公共表就会牵连全局。兼顾事务一致性与代码隔离的常见方案是模块化单体（Modular Monolith）：整个业务后端仍打包为单个服务部署、共用单库事务，但在代码内部严格切分公共平台底座与各个独立的业务模块，整体结构如图 2.1 所示。

在图 2.1 下半部，公共平台底座集中维护全系统共用的账号会话、企业与项目成员表、对象存储文件登记表以及配额账本；右侧的业务模块 A、B、N 分别对应具体的产品功能线（如智能报告审阅、竞争情报监测等），每个模块只读写带有本模块专属前缀的 MySQL 表，并在模块内部定义所需的 Agent 分析任务，禁止直接去查底座或其他模块的私有表。模块与底座之间通过依赖注入（Dependency Injection, DI）衔接：依赖注入是指模块代码不直接导入底座的内部实现文件，只声明自己需要一个符合特定函数签名的接口对象（如 FileService ），由程序启动时的应用组装层把底座的真实实现传入模块。这样平时所有模块都在同一进程内高效调用；日后若模块 A 负载激增需要独立部署到另一台服务器，只需把注入的本地函数换成远程HTTP 客户端即可，模块 A 内部代码无需改动。
